# 评测明细与复现说明

本文件由 `scripts/make_eval_report.py` 从 `knowledge/eval/eval_output/**/eval_scores_*.csv` 自动生成，
与 README 中的图表同源，避免手工誊抄误差。

## 1. 评测设置

| 项目 | 说明 |
| --- | --- |
| 评测框架 | Ragas（LLM-as-judge） |
| 评测集 | 万用表商品 QA，10 题（`万用表_qa.csv`，question / ground_truth） |
| 生成链路 | `knowledge.processor.query_process.main_graph.query_app`（真实链路，非 mock） |
| 检索上下文 | 取 `state.reranked_docs`，即 rerank + 截断 + 保底注入之后的最终上下文 |
| Judge / Embedding | 复用项目 `qwen-flash` 与 BGE-M3（自定义 `BaseRagasEmbeddings` 适配器） |
| 归档方式 | 每次运行按时间戳落 `eval_scores_*.csv` / `eval_details_*.csv` |

指标含义：

| 指标 | 看什么 |
| --- | --- |
| faithfulness | 答案的每句结论是否都能在上下文里找到依据 |
| answer_relevancy | 答案是否正面回答了这个问句 |
| context_precision | 上下文中相关内容是否排在前面（信噪比） |
| context_recall | 参考答案的要点是否被上下文覆盖 |
| answer_correctness | 与 ground_truth 的事实 / 语义一致度 |
| context_entity_recall | 参考答案里的实体被上下文覆盖的比例 |

## 2. 三轮总览

| 阶段 | faithfulness | answer_relevancy | context_precision | context_recall | answer_correctness | context_entity_recall | 有效应答 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 基线 · 一轮测试 | 0.183 | 0.174 | 0.200 | 0.183 | 0.255 | 0.060 | 2 / 10 |
| 优化 1 后 · 二轮测试 | 0.910 | 0.901 | 0.845 | 0.867 | 0.685 | 0.232 | 10 / 10 |
| 优化 2 后 · 最终 | 0.900 | 0.921 | 0.847 | 0.967 | 0.726 | 0.298 | 10 / 10 |

> 基线（一轮测试）跑了两遍，指标取两次运行的合并均值——LLM 生成的随机性会让单次结果上下浮动 1~3 个百分点。

- **基线 · 一轮测试**：入口没有意图维度；商品名对齐阈值过严，10 题中 8 题被「请确认产品」拦截
- **优化 1 后 · 二轮测试**：意图门控 + 商品名对齐加固后，10 题全部进入检索链路
- **优化 2 后 · 最终**：加入 Rerank 本地知识保底注入，并收紧截断

> 值得单独看第 10 题（操作温度 + 湿度）：二轮测试里它的 `context_recall = 0.000`，最终一轮是 `1.000`——同一道题、同一条链路，差别只在「本地权威 chunk 有没有被 pin 回上下文」。

## 4. 单题调试轨迹：温度 + 湿度

问题：`RS PRO RS-12 数字万用表：仪表的操作环境温度和湿度有什么要求？`

| 运行 | context_recall | context_precision | answer_correctness | context_entity_recall | 上下文条数 | 是否覆盖湿度 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 第 1 次 `20261018_195129` | 0.200 | 1.000 | 0.581 | 0.000 | 3 | 是 |
| 第 2 次 `20261018_205154` | 1.000 | 0.917 | 0.639 | 0.000 | 5 | 是 |
| 第 3 次 `20261018_210013` | 1.000 | 0.500 | 0.639 | 0.111 | 5 | 是 |
| 第 4 次 `20261018_215718` | 1.000 | 0.500 | 0.602 | 0.000 | 4 | 是 |

关键对比（第 1 次 vs 第 2 次）：

- 第 1 次：`…关于相对湿度的要求，参考内容中未明确列出具体数值。` → context_recall 0.20
- 第 2 次：`- 操作环境温度：32°F～122°F（0°C～50°C）  - 相对湿度：操作…` → context_recall 1.00

第 3、4 次运行里 precision 掉到 0.50，是补上下文带来的副作用（补进来的 chunk 并非条条相关），也是后来引入「断崖截断 + 只 pin 1 条本地 chunk」的依据：**召回要保底，精度靠截断**。

## 5. 复现

```bash
# 1) 准备评测集：含 question / ground_truth 两列的 CSV，改 eval_main.py 里的 QA_CSV_PATH
pip install ragas datasets pandas

# 2) 跑评测（会真实调用检索链路，并把历史写入 Mongo）
python -m knowledge.eval.eval_main

# 3) 结果落在 knowledge/eval/eval_output/<timestamp>/
#    eval_scores_*.csv  逐题指标   eval_details_*.csv  逐题问答与上下文

# 4) 重新生成本文件
python scripts/make_eval_report.py
```

## 6. 这些数字的可信度边界

- **样本量小**：10 题、单商品领域，指标适合做「改前改后」的相对比较，不宜当作绝对能力宣称。
- **Judge 方差**：Ragas 用 LLM 打分，同一份数据重跑会出现 ±0.02~0.05 的抖动，结论只取量级明显的差异。
- **entity_recall 长期偏低**：`context_entity_recall` 对中文专有名词（型号、单位）的抽取并不稳定，0.0 往往反映的是 judge 抽不出实体，而不是上下文真的缺实体——它在中文场景只作参考。
- **单题 n=1**：第 4 节的轨迹是同一道题的 4 次运行，用于定位问题，不做统计推断。
